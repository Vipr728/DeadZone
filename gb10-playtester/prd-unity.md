## 1. `unity/PlaytesterProject/Assets/Scripts/Player/` `[laptop-ok]`

- `PlayerController.cs` — reads Input System actions (`Move` as a `Vector2`/1D axis, `Jump` as a button), applies horizontal velocity and jump impulse via `Rigidbody2D.linearVelocity`. Exposes public constants for move speed and jump force as `[SerializeField]` fields on a `PlayerConfig` ScriptableObject (not hardcoded) — **ML/RL lead needs these exact numbers to set `piece_config.yaml` ranges correctly, so measure and hand off actual move speed (u/s) and jump apex height/distance the moment this is playable, hour 0–4.**
- `PlayerConfig.cs` (ScriptableObject) — `moveSpeed`, `jumpForce`, `groundedCheckDistance`, all `# TUNABLE` from an Inspector-editable asset.
- Grounded check via `Physics2D.Raycast` or `OverlapBox` against a ground layer mask (configurable layer, not hardcoded string tag).
- **Input actions asset:** `PlayerControls.inputactions` with an action map containing `Move` (composite 1D, A/D or Left/Right) and `Jump` (button, Space), used for human playtesting only. **Locked decision (removes any need to coordinate with ML/RL lead on this):** the RL agent never touches the Input System device layer at all — `PlaytestAgent.OnActionReceived()` calls a `PlayerInputAdapter` component directly (`SetMove(float)` / `SetJump(bool)`), which `PlayerController` reads from instead of the raw Input System callback when a `PlaytestAgent` is present on the same GameObject. Same `PlayerController` code path serves human play and RL control; this is a Unity-side-only implementation detail Rahul owns end to end, and `prd-ml.md` only needs to know the two method names above.

## 3. `unity/PlaytesterProject/Assets/Scripts/Agent/` `[laptop-ok for code, gb10-only for real training runs]`

- `PlaytestAgent.cs : Agent` — implements:
  - `CollectObservations(VectorSensor sensor)` — calls `IObservationEncoder.Encode(sensor, playerState, tilemapWindow)`. The encoder is a separate class (`GridObservationEncoder.cs`) implementing a C# `IObservationEncoder` interface mirroring `prd-ml.md`'s Python-side spec, so swapping grid size or added fields is a new encoder class, never edits inside `PlaytestAgent`.
  - `OnActionReceived(ActionBuffers actions)` — maps discrete action branch to `PlayerInputAdapter.SetMove/SetJump`, computes progress-toward-goal delta since previous step, calls `IRewardStrategy.piece_progress_reward(delta)` + `step_time_penalty()`, adds via `AddReward()`.
  - `OnEpisodeBegin()` — Stage 1: calls `PieceComposer.Recompose()`. Stage 2: resets player to the level's `StartMarker` position, resets telemetry accumulator for the new episode.
  - Piece-completion and death/goal triggers: implemented as `OnTriggerEnter2D` handlers on piece-goal/hazard colliders that call `agent.AddReward(rewardStrategy.piece_completion_bonus())` / `EndEpisode()` per spec §2.3's dense-reward table — **not** computed inside `OnActionReceived`, since collider events are the natural Unity-side signal for discrete completion/death events.
- `RewardStrategies.cs` — C# mirror of `prd-ml.md`'s `IRewardStrategy`; `RewardConfigAsset` ScriptableObject generated from `reward_config.yaml` via the same sync-script pattern as `PieceLibraryConfig`.
- `PlayerInputAdapter.cs` — the bypass-Input-System control surface referenced in §1 above; this is what makes `PlaytestAgent` control the player "exclusively through a fixed input interface" per spec §2.6 without literally driving OS-level input events.

## 4. `unity/PlaytesterProject/Assets/Scripts/EditorTool/` `[laptop-ok]`

The primary demo-facing polished surface. One `EditorWindow`, split into panels (separate files, not one giant class):

- `PlaytesterEditorWindow.cs` — main window, tab/panel switcher.
- `LevelSelectionPanel.cs` — GameObject picker for Player, Tilemap picker for the level, populated via `EditorGUILayout.ObjectField`.
- `TrainingControlPanel.cs` — buttons: "Fine-tune on this level" (invokes `finetune_stage2.sh` as a subprocess via `System.Diagnostics.Process`, streams stdout into the window), "Load pre-trained checkpoint" (reads `contracts/checkpoint_manifest.schema.json`, populates a dropdown of available checkpoints per level).
- `ExportPanel.cs` — **the Export step, resolving the Exports/-vs-Builds/ ordering contract (`PRD.md`'s async-independence section, `prd-infra.md` §1/§4).** One button, "Export level for training." On click, in this exact order:
  1. Calls `BuildPipeline.BuildPlayer` (Unity Editor API, called directly since this runs inside the Editor process — no separate headless invocation needed) targeting `unity/PlaytesterProject/Builds/<level_id>/<level_id>.<ext>`.
  2. Only if that build succeeds, writes `unity/PlaytesterProject/Exports/<level_id>/level_export.json` — `{"level_id": str, "build_path": str, "scene_path": str, "exported_at": str}`.
  This ordering is the entire contract: by the time OpenClaw's `LevelWatcher` (`prd-infra.md` §4) sees a marker, the matching build already exists — it never needs to poll or wait for one. `TrainingControlPanel.cs`'s manual "Fine-tune on this level" button can call `finetune_stage2.sh` directly without going through this panel at all (the human clicking it is confirmation enough that a build already exists) — both surfaces converge on the same build/script, this panel just also opens the automatic-via-OpenClaw path by writing the marker.
- `PlaybackPanel.cs` — "Run agent on this level" button launches `run_playtest.sh --execution-mode remote`, which keeps Unity local and runs primary `--resume --inference` policy inference on the GB10. It shows live position/telemetry during playback and exposes Sentis (§5) as a compatibility check/emergency fallback.
- `ReportPanel.cs` — displays the structured report (`contracts/report.schema.json`) once Abhi's pipeline writes it, read from a file path convention (`infra/config.yaml`'s output dir) polled or watched via `FileSystemWatcher`.

**Subprocess invocation contract (locked, see `prd-ml.md` §5 — do not deviate independently):** the Editor tool shells out to `uv run rl/scripts/finetune_stage2.sh --level-id <id> --checkpoint-in <path> --checkpoint-out <path> --output-manifest <path> --execution-mode remote` via `System.Diagnostics.Process`, reading stdout/exit code for status. The orchestration layer assigns the trainer port and SSH tunnel; Unity does not hardcode either a GB10 address or port. Level builds remain at `unity/PlaytesterProject/Builds/<level_id>/<level_id>.<platform-extension>`.
